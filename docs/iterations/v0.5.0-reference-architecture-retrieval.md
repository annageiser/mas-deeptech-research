**Status:** DESIGN / PLAN. No code has been written. This doc specifies the
change for review before implementation.
**Date:** 2026-07-07
**Author:** Anna (+ Claude)
**Depends on:** v0.4.44 (ddgs), v0.4.45 (reasoning off). Supersedes the

## 1. Purpose

The thesis derives an **optimal reference architecture** for a deep-tech-signal
research MAS from the literature (theory), then **recreates** it (practice) as
two systems that instantiate the two dominant paradigms:

- **System A (MASFactory)** — a *predefined / modular* pipeline (graph
  orchestration): Planner → Retriever → per-actor Loop(Extractor → Classifier →
  Reranker → Critic) → Analyst → Persistence.
- **System B (Hermes)** — an *agentic* pipeline (autonomous loop): one agent
  per actor decides its own tool calls and emits signals.

Today the two systems differ not only in **architecture** (the intended
independent variable) but also in **retrieval substrate** (a confound): A pulls
full text from Google News + Bing + arXiv + website scraping + EPO patents,
while B sees DuckDuckGo *snippets* only. This doc makes both systems implement
the **same reference retrieval layer**, so the measured difference isolates the
paradigm, and both gain the recall/quality the reference prescribes.

## 2. Theoretical grounding (literature → requirements)

The agentic-RAG literature distinguishes two paradigms that our two systems map
onto directly:

- **Predefined / Modular-RAG reasoning** — fixed, rule-based pipelines of
  interoperable modules (retriever, reranker, generator). → **System A.**
- **Agentic reasoning** — the LLM acts as an autonomous agent that decides
  *when, what, and how* to retrieve. → **System B.**

  (Reasoning Agentic RAG survey — *Reasoning RAG via System 1 or System 2*,
  arXiv:2506.10408; *Agentic RAG: A Survey*, Singh et al.)

Deep-research-agent references (*Deep Research Agents: A Systematic Examination
and Roadmap*, arXiv:2506.18096; Stanford **STORM**, Shao et al. 2024;
**GPT-Researcher**) converge on a retrieval layer with these capabilities. We
adopt them as the reference requirements:

| # | Reference requirement | Rationale (lit.) |
|---|---|---|
| **R1** | **Broad meta-search recall** over the open web | DR agents "automate … web search, evidence aggregation"; GPT-Researcher decomposes into parallel web searches |
| **R2** | **Full-text extraction**, not snippets | grounding claims in *retrieved sources* (STORM); snippets under-support extraction/typing |
| **R3** | **Structured academic + IP sources** | domain signal channels — arXiv papers, patents (Spence 1973 costly signals; Ehrenthal four-signal) |
| **R4** | **Recency-aware** windowing | signal freshness is a first-class thesis metric |
| **R5** | **Source-grounded citations** (exact URL + verbatim quote) | anti-hallucination; every signal traceable |
| **R6** | **Reproducibility** of the substrate | self-hosted, version-pinned, no external quota |

System A already satisfies R2/R3/R4/R5 partially and misses R1 (no open-web
meta-search). System B satisfies R1 weakly (DDG only) and misses R2, giving
thin snippet-only evidence that hurts R5 (exact link / quote) and downstream
`signal_type` assignment.

## 4. Target design

### 4.1 Shared self-hosted SearXNG (R1, R6) — both systems
- Add a `searxng/searxng` service to `docker-compose.yml` (internal network,
  not exposed publicly). Pin the image digest; commit the `settings.yml`
  (enabled engines, JSON format) for reproducibility.
- **System B**: install the bundled-optional `searxng-search` skill; set
  `SEARXNG_URL=http://searxng:8080`; add to `--skills`.
- **System A**: new `collection/websearch.py` that queries the same SearXNG
  JSON API and feeds hits into the Retriever funnel (then full-text scraped by
  the existing `website.py` path).

  "scrapling[all]"` + `scrapling install`); add to `--skills`.

  `source_url` / `evidence_quote`.

  with the Nvidia `Worker 32/32` throttle this lengthens System B runs. Mitigate
  by lowering `agent.max_turns` and limiting stealth-mode use.

### 4.3 Keep architecture-native components
A keeps its deterministic collectors + reranker/critic modes; B keeps its
agentic loop + `arxiv`/`blogwatcher` skills. Only the **open-web substrate** is
unified. This is the point: identical retrieval capability, different
orchestration paradigm.

## 5. Why a shared substrate (comparison validity)

If A and B used *different* web-search sources, any difference in yield/quality
could be attributed to the sources rather than the architecture — the same
comparison-validity defect v0.4.36 fixed for the *model* dimension (40× param
gap). Unifying on one SearXNG instance controls the retrieval confound so the
§3.5 comparison measures **modular-graph vs agentic-loop**, not
"Bing+scrape vs DuckDuckGo". This is the stronger, more defensible design.

## 7. Measurement / evaluation design

This change alters both architectures, so it **resets the clean-comparison
window** (as v0.4.36 / v0.4.38 did). Tag it `v0.5.0`, restart the eval window,
and treat pre-change data as the **baseline**. To evidence the expected
improvement (more, more-recent, higher-quality signals), report baseline vs
post on:

- **Yield** — new signals / run / actor.
- **Recency** — distribution of (run_date − signal_publication_date); expect a
  shift toward more recent.
- **Quality** —
  - % signals with a resolvable exact `source_url` (not a search-engine
    redirect),
  - % with `signal_type` assigned + four-dimension coverage,
  - mean `confidence`,
  - a small **human-rated precision** sample (Anna labels N per system).
- **Cross-system** — the same metrics per architecture, on the *shared*
  substrate, so the delta is attributable to the paradigm.

## 8. Risks & trade-offs

- **Image size / latency** — Playwright (Scrapling) is heavy; B runs slow under
  the Nvidia throttle. Accept, and tune `max_turns`.
- **Validity** — invalidates cross-window comparisons; must be a deliberate,
  documented version bump with a fresh eval window.
- **Scraping ToS / politeness** — Scrapling stealth/anti-bot must respect
  robots/ToS; restrict to public pages, add rate limiting.
- **SearXNG upstream throttling** — individual engines can rate-limit the
  instance; enable several engines and cache. Still far more robust than a
  single keyed API with a monthly quota.
- **Reproducibility upside** — self-hosted SearXNG is *more* reproducible than
  DDG/Tavily; pin image + settings and record engine set in the appendix.

## 9. Decisions (resolved 2026-07-07)

1. **SearXNG engine set** — enable a diverse, pinned set for recall + resilience
   + reproducibility: general = Google, Bing, DuckDuckGo, Brave, Startpage,
   Qwant, Mojeek; news = Google News, Bing News; academic = arXiv, Semantic
   Scholar, Crossref, Google Scholar; IP = **Google Patents**. Diversity
   maximises R1 recall and survives any single engine throttling; the pinned
   `settings.yml` gives R6 reproducibility. (Exact engine IDs verified at
   Stage 1.)
2. **Patents** — **revised during Stage 1 implementation:** SearXNG has **no
   built-in patents engine** (verified against `/config` — 279 engines, zero
   patent matches; a `google patents` entry fails to load). So patents parity
   for System B **cannot** come from the shared SearXNG and is **deferred to a
   dedicated patent channel** (a later stage): System A keeps its authoritative
   **EPO OPS** API; System B gains a patent channel via **EPO OPS** and/or
   **WIPO Patentscope** (PCT, has an API), with **Swissreg** for CH-national
   filings not reached via the EP route. EPO *Register* (register.epo.org) is
   legal-status/file-wrapper data, secondary to OPS for signal detection. Until
   then, both systems satisfy R3 on the **academic** axis via the shared
   SearXNG (arXiv, Google Scholar, Semantic Scholar, OpenAlex, PubMed,
   Crossref, OpenAIRE); patents remain a System-A-only channel (an honest,
   documented asymmetry to note in §4.1.4 until the patent channel ships).
3. **System B `max_turns` / stealth budget** — lower `agent.max_turns` 30 → **12**
   (enough for several searches + a few full-text extracts + synthesis, bounded
   so the Nvidia `Worker 32/32` throttle can't wedge a run). Scrapling default =
   plain HTTP / dynamic fetch; reserve **stealth mode only as a per-page
   fallback** (it runs a real browser, +5–15 s/fetch). Bounds runtime and
   throttle exposure while keeping full-text extraction.
4. **Eval window** — collect **≥14 days (target 21)** of post-change daily runs
   for BOTH systems before locking the §3.5 "post-v0.5.0" numbers; treat all
   pre-change data as baseline. 14 days × 40 actors smooths day-to-day variance
   (news cycles, engine hiccups); align the exact window to the pre-registration
   (§5/§7). Report baseline-vs-post per the metrics in §7.
