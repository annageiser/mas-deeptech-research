# v0.4.44 — revert the System B OpenRouter key split (hotfix)

**Date:** 2026-07-07
**Closes:** 2026-07-07 zero-signal outage — both daily reports (System A
MASFactory + System B Hermes) rendered via the v0.4.36 zero-signal
short-circuit: `New signals: 0` across all 40 seeded actors, runs `ok`,
0 errors.
**Scope:** two edits (`docker-compose.yml`, `.env.example`), this doc. No
schema, no dep, no Python. Operator must update `.env` on the VPS and
`docker compose up -d hermes`.

## Problem

Commit `16d0156` (2026-07-05) added a per-system OpenRouter key to the
hermes service:

```yaml
# hermes service, docker-compose.yml
environment:
  OPENROUTER_API_KEY: ${OPENROUTER_API_KEY_SYSTEM_B:-${OPENROUTER_API_KEY}}
```

The intent was isolation — give System B its own key so a rate-limit storm
on one system couldn't starve the other, and so OpenRouter's dashboard
showed a clean per-system breakdown for the reproducibility appendix.

In practice the dedicated key (`OPENROUTER_API_KEY_SYSTEM_B` in the VPS
`.env`) sits on OpenRouter's **50-request/day** free tier (an account
holding <10 credits), while the shared primary key is on the **1000/day**
tier (>=10 credits). A single hermes cron tick issues far more than 50
requests: 40 actors × (primary attempt + qwen fallback retry) × several
tool-calling rounds each. The key's daily budget is exhausted within the
first few actors; every subsequent `hermes chat` call comes back empty, so
each actor persists `signals: []`.

Because an actor that returns a *parseable* empty result counts as `OK`
(not `FAIL`) in `collect_all_actors.sh`, the run still closes `status=ok` —
which is why the report shows "1 run ok / 0 errors" rather than an error
run. `persist_signals.py` records no `token_usage` rows for System B, so the
report's "Token spend: 0 in / 0 out / 0 calls" line is always zero for
System B and is not diagnostic here.

## What this hotfix does — and does not — cover

**Covers:** System B's throttling. Removing the override makes hermes
inherit the shared 1000/day `OPENROUTER_API_KEY` from `env_file`, the same
key System A and the reports container already use. This restores the
single-key behaviour that produced signals daily through 2026-07-01.

**Does not cover:** System A also reported zero signals on 2026-07-07 with
**0 input/output tokens** — meaning the primary model produced no usable
output at all. System A was already on the 1000/day key, so the key split
does not explain it. The leading hypothesis is that the free primary
`nvidia/nemotron-3-ultra-550b-a55b:free` (a reasoning model) is returning
reasoning-only / empty visible bodies — the recurring failure mode from
v0.4.30 / v0.4.34 that v0.4.43 flagged as unresolved — and that
`FailoverLegacyOpenAIModel` does not fail over on that case (it only fails
over on the OpenRouter "no-choices" `TypeError`). **This needs VPS log
confirmation before a fix lands** (see Follow-ups). This hotfix deliberately
keeps the Nemotron primary so the next run's audit folder captures the
Nemotron failure signature cleanly rather than masking it with a model swap.

## Under the Hood

- **`docker-compose.yml`** — dropped the `OPENROUTER_API_KEY:
  ${OPENROUTER_API_KEY_SYSTEM_B:-${OPENROUTER_API_KEY}}` override from the
  hermes `environment:` block. Left an explanatory comment pointing here.
- **`.env.example`** — removed the `OPENROUTER_API_KEY_SYSTEM_B=` line and
  its doc block; replaced with a NOTE recording that the split was trialled
  and reverted, and that the single `OPENROUTER_API_KEY` must be on the
  1000/day tier (account >=10 credits).
