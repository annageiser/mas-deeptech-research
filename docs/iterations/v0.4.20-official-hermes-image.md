# v0.4.20 — System B uses the official NousResearch Hermes Agent image

**Date**: 2026-06-12
**Trigger**: Anna's directive: *"System B should now be the official Hermes Agent that can be downloaded from GitHub from Nous Research, not the rebuild you did"*.

## What changed

The wrapper image's base changes from **local build of the submodule source** to the **official published image from Docker Hub**:

| Before (v0.3.0 → v0.4.19) | After (v0.4.20) |
|---|---|
| `FROM hermes-upstream:${UPSTREAM_TAG}` (built locally from `systems/hermes/upstream/`) | `FROM nousresearch/hermes-agent:v2026.6.5@sha256:9ad3b04ec916ea2c2da22358fd43b024c788d74073210695af88bfc2e63869b4` |
| Upstream build: 10-15 min, 4.65 GB image | Image pull: ~1 min, 1.09 GB image |
| Pinned via `git submodule ... ba44de06` (commit SHA) | Pinned via digest (`@sha256:…`) on the published image |
| Required `docker build -t hermes-upstream:local systems/hermes/upstream` before `docker compose build hermes` | Just `docker compose build hermes` |

The submodule at `systems/hermes/upstream/` is **kept** as a source-code reference for the thesis defence and for inspecting upstream's implementation when needed. It's no longer on the build chain.

## Why this matters

1. **Honesty in the thesis defence.** Anna's right: "we built it ourselves from source" reads weaker than "we used the official binary released by Nous Research." Same code (NousResearch CI builds from the same source we had), better story.

2. **Reproducibility.** Digest-pinning (`@sha256:9ad…`) is *stronger* than git-SHA pinning of the source — the digest hash covers the exact built artefact including the build environment, not just the source tree.

3. **Smaller image.** The official image is 1.09 GB (dev dependencies stripped) vs our local build's 4.65 GB. Faster pulls on the VPS, less disk pressure, less network when restoring from backup.

4. **Faster iteration.** New cron / smoke runs no longer need a 10-15 min upstream rebuild. `docker compose build hermes` now finishes in ~30 s — only the thin wrapper layer (our ddgs install + skill + scripts) is rebuilt.

## What didn't change

- The agent CLI itself — same source code, same behaviour. Version v2026.6.5 was released by upstream on 2026-06-05 (the submodule `ba44de06` we had was main-tip at the time of installation, so very close to v2026.6.5).
- Our wrapper additions: `ddgs` install, `/opt/swiss-quantum/` directory, seed-hook, persister, skill, cron entrypoint. Identical to v0.3.0.
- The Caddy / API / web / MASFactory containers — untouched.

## Files changed

## How to bump the image version later

When NousResearch releases v2026.7.x:

```bash
# 1. Get the digest for the new tag
curl -s "https://hub.docker.com/v2/repositories/nousresearch/hermes-agent/tags/v2026.7.0" \
  | python3 -c "import json,sys; print(json.load(sys.stdin)['digest'])"

# 2. Edit systems/hermes/Dockerfile — replace BOTH the tag and the digest:
#    FROM nousresearch/hermes-agent:v2026.7.0@sha256:NEW_DIGEST

# 3. Optionally update systems/hermes/upstream submodule to the matching SHA
#    for source-reference consistency:
git -C systems/hermes/upstream fetch
git -C systems/hermes/upstream checkout <commit-for-v2026.7.0>

# 4. Commit + push + docker compose build hermes
```

Document the bump in a new `docs/iterations/vX.Y.Z-hermes-upstream-bump.md` so the thesis can cite the exact version used during the empirical-evaluation window.

## Note on the submodule

The submodule at `systems/hermes/upstream` is currently at commit `ba44de06` (main HEAD at the time we installed). The official image we now pull is `v2026.6.5` (commit `1a3b04a` or similar — TBC by inspecting the published image's `/opt/hermes/.hermes_build_sha` file).

These are close but not identical. For thesis-defence accuracy, the canonical version is **what the image actually contains** (digest `9ad3b04ec916ea2c2da22358fd43b024c788d74073210695af88bfc2e63869b4`), not the submodule SHA. The submodule stays in the repo for source-code lookup convenience but is no longer load-bearing.

If you want full alignment, point the submodule at the v2026.6.5 tag:

```bash
cd systems/hermes/upstream
git fetch --depth 1 origin tag v2026.6.5
git checkout v2026.6.5
cd ../../..
git add systems/hermes/upstream && git commit -m "hermes: pin submodule to v2026.6.5 (matches Docker image)"
```

Worth doing before the thesis defence.
