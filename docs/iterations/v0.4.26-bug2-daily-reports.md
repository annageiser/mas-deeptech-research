# v0.4.26 — Bug 2 fix: decouple daily reports from scrape success

**Date**: 2026-06-12
**Closes**: Bug 2 (#119) — Daily reports missing on /reports page after 2026-06-10

## What broke

Daily report entries on https://mas-deeptech-research.cloud/reports stopped
landing for most days after 2026-06-10. Two compounding causes:

### Cause 1 — chain `&&` in cron swallows the daily report on scrape failure

Each system's cron entry ran:

```
... scrape ... && ... daily report ...
```

With `&&`, if the scrape exited non-zero (network blip, OpenRouter quirk,
container error), the daily report never even attempted to fire. Across
Hermes Phase B (2026-06-10 → -11), every Hermes scrape errored at least
once. Each error swallowed that day's daily report along with it.

This is a *thesis-narrative* bug, not a real-cron bug. The daily report is
supposed to be a chronological log entry. A gap on the /reports page makes
it look like nothing happened, when actually "scrape errored, 0 new
signals" happened — and that's information worth recording.

### Cause 2 — VPS-side cron file may still be the Firecrawl-scare weekly version

Independent of the chain operator, the in-repo `crontab.sample` files
were briefly flipped to Monday-only-weekly during the Firecrawl-budget
scare around 2026-06-09. v0.4.19 restored them to daily in the repo,
but a `sudo cp .../crontab.sample /etc/cron.d/...` step on the VPS host
is what actually applies the change — and that step is easy to forget.
If the host's cron entry is still the weekly version, no daily fires
on Tue-Sun regardless of the chain operator.

## What ships

### `systems/masfactory/crontab.sample`

Chain operator before the daily-report step changed from `&&` to `;`:

```diff
- 0 2 * * * root ... masfactory run-once ... && ... reports daily --system masfactory ...
+ 0 2 * * * root ... masfactory run-once ... ; ... reports daily --system masfactory ...
```

The `&&` after `cd /opt/mas-deeptech-research` is preserved — we still
want the docker command to abort if `cd` fails. Only the
`scrape → report` step is decoupled.

### `systems/hermes/crontab.sample`

Same change:

```diff
- 0 5 * * * root ... hermes ... && ... reports daily --system hermes ...
+ 0 5 * * * root ... hermes ... ; ... reports daily --system hermes ...
```

Plus a comment block explaining the Phase B history so a future reader
knows why the operator looks different from the masfactory entry it
mirrors.

### Why this is safe

The daily-report prompt already handles `signal_count = 0`:

> Line 39, `systems/reports/prompts/daily.md`:
> "If the day had zero signals, say so explicitly and note why (likely
> cause: free-tier rate limit, scrape failure, planner skipped most
> actors). Don't fabricate."

So when the scrape errors and the report still fires, the LLM produces
a "no new signals today — scrape errored" entry rather than crashing
or fabricating. The /reports page gets a row for every day instead of
gaps.

## Operator runbook (verify + apply on the VPS)

```bash
# 1. SSH to the VPS
ssh root@187.127.87.208
cd /opt/mas-deeptech-research

# 2. Pull the updated crontab.sample files
git pull

# 3. Diff the current cron entries against the new samples
diff /etc/cron.d/mas-deeptech-research-masfactory \
     systems/masfactory/crontab.sample
diff /etc/cron.d/mas-deeptech-research-hermes \
     systems/hermes/crontab.sample
# Both should now show ONLY the && → ; change. If you see other diffs
# (e.g. dom or dow fields differ), the VPS cron is stale beyond Bug 2
# — overwrite it from the sample.

# 4. (Re-)install the cron entries with the new versions
sudo cp systems/masfactory/crontab.sample \
        /etc/cron.d/mas-deeptech-research-masfactory
sudo cp systems/hermes/crontab.sample \
        /etc/cron.d/mas-deeptech-research-hermes
sudo chmod 0644 /etc/cron.d/mas-deeptech-research-{masfactory,hermes}
sudo systemctl restart cron

# 5. Verify cron picked them up
sudo systemctl status cron --no-pager
ls -la /etc/cron.d/mas-deeptech-research-*
```

Then the next scheduled tick (04:00 / 05:00 Europe/Zurich) writes a
daily report regardless of scrape outcome. Confirm by visiting
https://mas-deeptech-research.cloud/reports the morning after.

## Acceptance criteria

- `/reports` has an entry for every day going forward.
- On days where the scrape errors, the daily report still fires and
  says so explicitly (matches the prompt's "zero signals" branch).
- No silent gaps on the page.

## What this is NOT

- **Not** a fix for the historical gaps from 2026-06-10 → -11 — those
  daily reports were never generated and there's no useful way to
  retroactively synthesise them (the snapshot data they would have
  read was already corrupted by the Phase B failures). The /reports
  page will show those gaps as missing rows forever; the fix prevents
  *future* gaps.
- **Not** a change to the cron *schedule* — still daily at 02:00 / 05:00
  Europe/Zurich. Only the chain operator changes.
- **Not** a change to the report prompt or generator — same code, same
  prompt, just executed in more cases than before.

## Threats to validity touched

Closes one implicit row in `docs/threats-to-validity.md`: "we silently
lose `/reports` entries when a scrape fails, making the audit trail look
worse than it is." After v0.4.26 the audit trail is complete by
construction: every scheduled day has a corresponding markdown row, and
days with errors are explicitly self-described in their report bodies.
