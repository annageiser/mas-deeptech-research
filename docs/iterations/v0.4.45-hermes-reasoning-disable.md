# v0.4.45 — Hermes: disable reasoning so Nemotron emits visible JSON (hotfix)

**Date:** 2026-07-07
**Closes:** System B (hermes) persisting 0 signals for 3+ days. Part 2 of the
2026-07-07 zero-signal investigation (part 1 = search backend, v0.4.44 +
Tavily→ddgs; part 0 = System A duplicate-cron, see
`masfactory-duplicate-cron-race`).
**Scope:** one config edit (`systems/hermes/config/cli-config.yaml`), this doc.
Requires a `docker compose build hermes` (the config is baked into the image,
then seeded to `$HERMES_HOME/config.yaml` on each container start).

## Problem

Even after the search backend was fixed (Tavily was credit-exhausted → HTTP
432 → `same_tool_failure_halt`; switched to ddgs in v0.4.44), a 1-actor
validation still yielded 0 signals. The agent stdout showed:

```
⚠️ Model returned empty after tool calls — nudging to continue
↻ Thinking-only response — prefilling to continue (1/2)(2/2)
⚠️ Empty response from model — retrying (1/3)(2/3)(3/3)
⚠️ Model produced reasoning but no visible response after all retries. Returning empty.
```

This is the v0.4.30 / v0.4.34 reasoning-model failure: `nvidia/nemotron-3-
ultra-550b-a55b:free` (a reasoning model) spends its output budget on
reasoning tokens and returns a reasoning-only, empty *visible* body after the
tool-call turns → the hermes parser finds no JSON block → `signals: []`.

### Root cause — the intended suppression was never wired to the right knob

The v0.4.38 config carried `model.reasoning: {exclude: true}` as "L1 server-side
reasoning suppression." A **live OpenRouter request dump** from a failing run
proved two things:

1. The hermes CLI **ignores `model.reasoning.*` entirely** (confirmed against
   the Hermes docs: reasoning is controlled *solely* by `agent.reasoning_effort`).
2. The CLI translates `agent.reasoning_effort: "low"` into the OpenRouter body
   param `reasoning: {enabled: true, effort: "low"}` — i.e. reasoning was
   **enabled** the whole time. The `exclude: true` key did nothing.

So the "three-layer defence" from v0.4.38 was effectively L2-only (the
`persist_signals.py` `<think>`-strip), which cannot recover a body that is
*entirely* empty, and L3 (the qwen fallback) which now 404s under
`provider_routing.require_parameters: true` (no free qwen endpoint exposes
tool-calling).

Direct OpenRouter probes of the same model confirmed the fix direction:
`reasoning: {enabled: false}` (and `{exclude: true}`) both return clean visible
JSON, while the enabled path is what leaks reasoning-only empties on the long
tool-heavy final turn.

## Under the Hood

`systems/hermes/config/cli-config.yaml`:

- `agent.reasoning_effort: "low"` → **`"none"`** — the single lever the CLI
  honours; disables reasoning so Nemotron returns its answer as visible content.
- Removed the dead `model.reasoning: {exclude: true}` block (it was ignored and
  misleadingly implied active L1 suppression). Replaced with a comment pointing
  here. L2 (`persist_signals.py` `<think>`-strip) still runs as a backstop.

Note on the architecture comparison: System A (masfactory) keeps Nemotron's
reasoning but *excludes* it from the response via the OpenAI SDK's
`extra_body={"reasoning":{"exclude":true}}` (which OpenRouter honours), so
System A still benefits from the model's reasoning internally. System B cannot
express `exclude` through the hermes CLI, so it runs reasoning **off**. This is
a real, documentable per-system difference (§3.4 / §4.1.4): both systems use the
same model slug, but System B's agent runs it in non-reasoning mode.

## Known remaining caveat

The free Nvidia endpoint throttles: `Upstream error from Nvidia:
ResourceExhausted: Worker local total request limit reached (32/32)`, hit even
within one actor's agent loop. So each actor is slow and retry-heavy (~6 min in
the smoke test). A full 40-actor cron run should still complete but will be
long; if it becomes a problem, options are lowering `agent.max_turns`,
staggering actors, or (future) a paid provider for System B only.
