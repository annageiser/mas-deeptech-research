# v0.4.19 — Defense as boolean flags (not a fifth signal_type)

**Date**: 2026-06-11
**Trigger**: Anna's design correction — `defense_engagement` should be a flag overlaid on the Ehrenthal four, not a fifth signal_type alongside them.
**Bundles**: Bug 1 (NULL signal_type backfill), Bug 3 (legacy label fallback in API), and the dependent prompt + persister changes.

## The design problem v0.4.2 had

v0.4.2 added `defense_signals` as a 5th signal_type alongside Ehrenthal's four. That was wrong on two counts:

1. **Categorical overlap.** A defense contract IS a customer co-creation event. A NATO consortium membership IS a community-ecosystem signal. Marking it as `defense_signals` only loses the underlying Ehrenthal classification — the categories aren't mutually exclusive.

2. **Different conceptual layer.** "Is this signal defense-related?" is a *boolean property* of any signal, not a *type* of signal. The right schema operator is a flag, not a category.

## The v0.4.19 model

Every signal has:

- `signal_type ∈ {legitimacy, customer_cocreation, community_ecosystem, future_trajectory}` — exactly one (Ehrenthal 2026).
- `dimension` — sub-category within the signal_type.
- `defense_engagement: bool` — true iff explicit defense / dual-use / DARPA / NATO / ITAR / EAR / military context.
- `defense_ambivalence: bool` — true iff actor publicly withholds info citing "national security" / "classified" / similar, OR distances itself from defense uses while accepting defense funding (Eisenberg 1984 strategic ambiguity).

Both flags default `false`. They are set INDEPENDENTLY of `signal_type`. A single signal can have both flags true (rare but valid — e.g., announcing a DARPA contract while declining to comment on its specifics).

## Bug bundling

### Bug 1 — NULL signal_type backfill

Rows from pre-v0.4.0 data that weren't covered by the v0.4.0 dimension-rewrite map still had `signal_type = NULL`. The v0.4.19 migration includes a step-4 backfill that sets those to `community_ecosystem` with `dimension_legacy` preserving the original value. Conservative default — these rows are flagged for human review when the gold-standard set is constructed (C.1).

### Bug 3 — Unlabelled signal_types on `/signals` page

The API used to call `SIGNAL_TYPE_LABEL.get(key, key.title())`. Pre-migration rows with `defense_signals` (a valid key in v0.4.2 but not in v0.4.19) would render as "Defense Signals" rather than nothing — but only because of the title-cased fallback. After we removed `defense_signals` from the v0.4.19 map, that fallback would still apply, but it'd look like a normal label.

The v0.4.19 fix uses a three-step resolver: current map → legacy map → "(legacy: <key>)" annotation that's visibly different from any normal label. So a future stray value won't render as if it were a current category.

## Lessons-learned worth noting

The original v0.4.2 schema lasted about a week before this design issue surfaced. The right time to challenge "is this a category or a flag?" is at schema-design time, not after migration. For future schema work, ask: "could this value be true alongside any other value of its parent attribute?" If yes → flag, not category.

For the thesis lessons-learned chapter: this is a small but clean example of the constructive-research approach — the artefact's first iteration revealed a categorical conflation that the literature framing alone wouldn't have caught.
