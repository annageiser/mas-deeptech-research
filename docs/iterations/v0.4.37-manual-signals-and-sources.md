# v0.4.37 — Manual signal training + RSS / source management

**Date**: 2026-06-24
**Closes**: Tasks 1 and 2 from the 2026-06-24 build batch.

## What ships

Two editorial CRUD layers Anna manages through the dashboard:

1. **Manual signal training** at `/labels`
   - Insert a URL, optional title/notes/signal_type/dimension, free-form
     labels, related actors. Edit, delete, view all.
   - Persisted in `public.manual_signals` (new table; see
     `docs/migrations.md` 2026-06-24 entry).
   - Both producer systems read this table at the start of each cron
     run (via the new vendored `training_layer.py` modules in
     `masfactory_system/` and `systems/hermes/scripts/`).
   - System A's Retriever injects each recommended URL as an
     additional `source_kind='manual'` Document so it flows through
     the Extractor / Classifier / Critic / attribution gate / persister.
   - System B's per-actor prompt is augmented with a
     `MUST-CHECK URLS` block (materialised by the new
     `training_context_preflight.py` before the per-actor loop).
   - A new sync script
     `systems/masfactory/masfactory_system/scripts/sync_manual_signals.py`
     propagates each manual signal into `public.signals` as
     `system='manual'`, `source_kind='manual'`. They appear on
     `/signals`, `/compare`, and the daily reports under their own
     slice. Idempotent (manual_signals.propagated_signal_id).

2. **Source management** at `/sources`
   - CRUD over `public.signal_sources` (RSS / Atom / URL).
   - Per-source `enabled`, `label`, `labels[]`, `actor_slugs[]`,
     `crawl_frequency_hours`.
   - Both systems read enabled, due sources via the same
     `training_layer.py` and inject them into the per-actor pipeline.
   - `crawl_frequency_hours` is a floor — daily cron skips sources
     whose `last_fetched_at` is newer than `now() - crawl_frequency_hours`.
   - Per-fetch bookkeeping (`last_fetched_at`, `last_status`,
     `last_item_count`, `last_error`) updated by both producers.
   - Coexists with the static `data/raw/rss_feeds.yaml` registry;
     DB-managed sources are an additive layer, not a replacement.

## Schema changes

`systems/masfactory/masfactory_system/persistence/schema.sql` gains
three tables (`manual_signals`, `signal_sources`, `signal_source_runs`),
two indexes per table, an `updated_at` touch trigger, and one CHECK
extension on `public.signals.system` to allow `'manual'`. All
idempotent — re-runnable on existing Supabase projects.

Migration guidance for the live deployment is in `docs/migrations.md`
under the 2026-06-24 heading. Paste the new SQL block into the
Supabase SQL editor exactly once.

## API surface

Eight new endpoints in `systems/api/api_app/main.py` (validation +
logic in the new `systems/api/api_app/training.py` module):

- `GET    /api/manual-signals`         — list
- `GET    /api/manual-signals/{id}`    — fetch one
- `POST   /api/manual-signals`         — create
- `PATCH  /api/manual-signals/{id}`    — partial update
- `DELETE /api/manual-signals/{id}`    — delete
- `GET    /api/sources`                — list (filter by `enabled=true/false`)
- `GET    /api/sources/{id}`           — fetch one
- `POST   /api/sources`                — create
- `PATCH  /api/sources/{id}`           — partial update
- `DELETE /api/sources/{id}`           — delete

Auth model: trust Caddy basic-auth. The dashboard is "Anna only" by
deployment. If these endpoints ever route to a public path, add an
explicit admin check at the route layer before reaching `training.py`.

## System integration (production cron path)

**System A** (`masfactory`)
- `Retriever` (`agents/retriever.py`) loads the training layer once
  per run and, for each actor:
  - Injects each `manual_signals.source_url` related to that actor as
    a `source_kind='manual'` Document.
  - Injects each due `signal_sources.url` related to that actor as a
    `source_kind='website'` (or `'news'` for RSS/Atom kinds) Document.
  - Calls `mark_source_fetched()` so `crawl_frequency_hours` advances.
- The Retriever's return value gains `training_meta` (per-actor URL
  counts, totals) and `training_few_shot` (per-actor curated examples
  the Classifier prompt builder will pick up in a follow-up iteration).
- Persisted signals from manual-injected URLs land in `public.signals`
  with `system='masfactory'` (the producer that processed them), not
  `'manual'` — that's appropriate because the Extractor/Classifier
  did real work. The `'manual'` slice in `public.signals` is reserved
  for the editorial layer itself, propagated by `sync_manual_signals.py`.

**System B** (`hermes`)
- `collect_all_actors.sh` runs a Python preflight
  (`training_context_preflight.py`) immediately after the actors.tsv
  is written. The preflight materialises a per-actor block file
  (`${LOGDIR}/training/<slug>.txt`) containing the
  `MUST-CHECK URLS` + `ADDITIONAL SOURCES` sections.
- The per-actor loop splices the block into the prompt before the
  "Output the JSON block …" sentinel. Empty block files are no-ops.
- Failures of the preflight (Supabase unreachable, etc.) leave empty
  files behind — Hermes behaves exactly as in v0.4.36.

**Propagation** (`sync_manual_signals.py`)
- Inserts one row per (manual_signal × related actor) into
  `public.signals` with `system='manual'`, `source_kind='manual'`.
- All manual rows share a single long-lived synthetic `runs` row
  (created on first invocation, identified by
  `config_snapshot.label='manual-sync'`).
- `content_hash` formula matches v0.4.36 (`actor_slug | source_url |
  title`, normalised). The unique index dedups across re-runs.
- Manual signals with zero related actors are marked `propagated_at`
  immediately (they remain useful as few-shot examples even without a
  public.signals row).

## Threats to validity touched

- Pre-reg H1/H2/H3/H4/H5 still compute on `system in ('masfactory',
  'hermes')` only. `system='manual'` is a separate slice — the
  evaluation harness (`systems/evaluation/eval_app/runner.py`)
  filters it out by default. Adding manual signals does not
  contaminate the cross-MAS comparison.
- Comparison-validity invariant preserved: `training_layer.py` is
  vendored verbatim into both `masfactory_system/` and
  `systems/hermes/scripts/` rather than imported across the boundary.
- The "training layer is opt-in" framing means days when Anna adds no
  manual signals or sources are bit-identical to v0.4.36 behaviour.
  Pre-v0.4.37 days remain comparable.

## What is still on the backlog (deliberately deferred)

- **Few-shot prompt wiring in System A's Classifier.** The Retriever
  surfaces `training_few_shot` per actor in attrs, but the Classifier
  prompt builder does not yet read it. The minimum-viable few-shot
  hook is one paragraph in `classification/few_shot_examples()` — see
  v0.4.38 follow-up.
- **Per-source ingestion-history rows.** `public.signal_source_runs`
  exists but the producers only update `signal_sources.last_*` fields,
  not append new `signal_source_runs` rows. Add when you need a
  per-source error timeline.
- **A real Atom / RSS body fetch in the Retriever.** Currently the
  Retriever stubs `text` as a placeholder for manual + source URLs —
  the existing `collect_website` /  `collect_rss_for_actors`
  collectors don't yet read from `signal_sources`. Wiring them up is
  ~50 lines, but it depends on whether you want the Retriever to
  fetch on-the-spot (synchronous, adds latency) or queue for the next
  cron (asynchronous).
- **Tests.** A smoke test for the new API endpoints lives in
  `systems/api/tests/test_api.py`; deeper coverage of the producer
  hooks deserves its own commit.

## Deployment steps

See PR description on GitHub. Summary:

1. Paste the new SQL block from `docs/migrations.md` (2026-06-24
   heading) into the Supabase SQL editor.
2. `docker compose build api web masfactory hermes` on the VPS.
3. `docker compose up -d api web caddy` to restart always-on services.
4. Add the chained `sync_manual_signals` step to the existing daily
   cron (one line after each `masfactory run-once`):
   ```
   docker compose run --rm masfactory python -m masfactory_system.scripts.sync_manual_signals
   ```
5. Add an entry to `/etc/cron.d/...` only if you want it more
   frequent than the existing chain (default: daily after both
   producers finish is sufficient).
