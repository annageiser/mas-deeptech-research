# v0.4.43 — reports LLM-failure short-circuit (hotfix)

**Date:** 2026-07-03
**Closes:** Missing daily reports for 2026-07-02 and 2026-07-03 (both systems). Signals were persisted, runs were logged, but the narrative synthesis crashed and the report file was never written.
**Scope:** one file edit (`systems/reports/reports_system/daily.py`), 6 unit tests, this doc. No env change, no schema change, no dep.

## Problem

The `/reports` page has entries every day from 2026-06-17 through 2026-07-01, then a hard two-day gap. Both systems missing for both days. Underlying evidence:

- `/api/compare?days=1` on 2026-07-03 shows System A collector runs and System B collector runs both fired, and System B persisted 9 new signals for 2 actors on 2026-07-02 (`inserted_at=2026-07-02T07:19:10 UTC`).
- The 2026-07-01 report exists and was generated at `2026-07-01T10:09:31 UTC` — so the reports service was still healthy that day.
- Between 2026-07-01 late and 2026-07-02 early, something started making the narrative LLM call fail. In `openrouter.py`, the client tries the primary model first and falls back to `settings.model_fallback`; when both fail the wrapper raises `RuntimeError("both models failed: ...")`. Pre-hotfix `daily.py` did not catch that RuntimeError.

The RuntimeError propagated up through `generate_daily` → `cmd_daily` → `runner.main()`'s top-level `except Exception`, which prints a traceback and exits 1. The cron chain (`... ; docker compose run --rm reports daily --system <sys>`) then completes with a non-zero exit but doesn't retry, and no report file lands on disk. From the /reports page's perspective, the day simply doesn't exist.

The zero-signal path already had a short-circuit (`daily.py:52`, added in v0.4.36) that wrote a fixed-template report without any LLM call. There was no equivalent for the LLM-failure case, which is the asymmetry this hotfix removes.

## Under the Hood

Two additions, one file:

- **`_llm_failure_template`** — a new template that mirrors `_zero_signal_template` but incorporates the real signal count, the real actor coverage, the real four-signal mix, and the top-3 signals by confidence for skimmability. Emits a "Why this report has no LLM narrative" section with the underlying error string so the /reports page shows what happened rather than silently disappearing. Ends with a `v0.4.43 LLM-failure short-circuit` provenance marker so a future reader can trace the fallback back to this doc.
- **`try / except` around the `client.chat()` call** — catches any exception (RuntimeError from the openrouter wrapper, network errors, response validation failures) and returns the stub instead of propagating. The exception message is truncated at 400 chars and inlined into the report body so the failure mode is visible without needing to log-dive.

The catch is intentionally broad (`except Exception`) so that a novel failure mode a future OpenRouter or provider change introduces still writes a stub rather than crashing. The alternative — enumerate `RuntimeError`, `RateLimitError`, `APIStatusError` etc. individually — was rejected because the goal is "the /reports page has an entry every day," and letting an unknown exception through defeats that.

Both the pre-existing zero-signal path (test `test_generate_daily_zero_signal_path_unchanged`) and the happy path (test `test_generate_daily_happy_path_unchanged`) are protected by regression tests that live alongside the new short-circuit test.

## Tests

`systems/reports/tests/test_llm_failure_short_circuit.py` — 6 tests, no network:

- `_llm_failure_template`: renders the summary correctly; top-3 signals sort by confidence; empty signals collapse to `"None."`; missing `signal_type_counts` renders zeros without raising.
- `generate_daily`: writes stub file when `client.chat()` raises RuntimeError, with `short_circuit="llm_failure"` and the truncated error surfaced in the return dict; the happy path still writes the LLM narrative verbatim; the zero-signal path still fires without calling the LLM (regression check).

All 6 pass locally on Python 3.11 with mocked SupabaseReader / OpenRouterClient.

## Follow-ups

- **Root cause of the 2026-07-02 LLM failure remains unidentified.** Once the guard is deployed, the next occurrence will produce a stub report whose "Underlying error" line names it. Likely candidates from the model listing on OpenRouter today:
  - Free-tier daily-quota exhaustion (account-wide, aggravated by masfactory's pre-v0.4.42 crash loop chewing through retries)
  - Provider rotation of Nemotron 3 Ultra `:free` under a different upstream
  - OpenRouter response validation change
- **Thesis limitation note (§4.1.4)**: the 2026-07-02 and 2026-07-03 `/reports` gap should be recorded in the operational-events paragraph alongside the pre-existing 06-12/13 outage. The pre-reg §5 metrics are unaffected (they read from Supabase directly), but the gap is real for a reader browsing chronologically.
- **Deferred**: adding a third fallback model (e.g. `meta-llama/llama-3.3-70b-instruct:free`) at the openrouter.py layer, so a two-model outage triggers a third try before the stub fires. Small change, worth doing in the next iteration.
