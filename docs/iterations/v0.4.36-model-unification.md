# v0.4.36 — Model unification between System A and System B

**Date**: 2026-06-24
**Closes**: Phase 10 re-verification finding R-1 (comparison-validity defect from 40× parameter asymmetry)

## What was wrong

After the v0.4.30→v0.4.35 free-tier failure chain, System B settled on
`meta-llama/llama-3.2-3b-instruct:free` — a 3B-parameter model. System A
was still on `nvidia/nemotron-3-super-120b-a12b:free` (120B params, a
reasoning model). The two systems were running on models 40× apart in
parameter count.

This invalidated the architecture comparison the thesis is built on:
any difference in §3.5 yield, mix, or classification quality between
System A and System B could be attributed to the model-class gap rather
than to the architectural difference (graph orchestration vs autonomous
loop). The §4.1.2 argument that "architecture matters" cannot survive
defence-question scrutiny under a 40× model-capability asymmetry — an
examiner asks "did you compare two architectures, or a 120B model on
one architecture vs a 3B model on another?", and the only honest
answer is the latter.

## What ships

### Default model for both systems

Both systems now default to `qwen/qwen3-next-80b-a3b-instruct:free`:
- **Free** (price = 0)
- **80B-class capability** (Qwen3 Next is a MoE; full 80B knowledge, 3B
  active params per token — comparable to Nemotron 120B in benchmark
  quality, far ahead of Llama 3.2 3B)
- **Plain instruct** — no `<think>` wrapper, so Hermes's response
  parser sees the visible body intact (the v0.4.30 failure mode does
  not recur)
- **Tool-calling supported on free providers** as of 2026-06-23
  verification

### Files changed

- `.env.example` — `MASF_MODEL_MAIN` and `HERMES_MODEL` both point to
  the unified model. `HRM_MODEL_*` lines removed (no code reads them;
  the actual env var Hermes uses is `HERMES_MODEL`).
- `systems/hermes/scripts/collect_all_actors.sh` line 257 — default
  changed from `meta-llama/llama-3.2-3b-instruct:free` to
  `qwen/qwen3-next-80b-a3b-instruct:free`. The long comment block
  documenting v0.4.30→v0.4.35 is replaced by a pointer to this doc.
- `systems/hermes/scripts/persist_signals.py` `_create_run()` — now
  also persists `model` and `tool_status` into `runs.config_snapshot`,
  so the eval harness can split §3.5 numbers per-model if a future
  asymmetry is introduced deliberately.

### What the operator must do

1. **Re-run the evaluation window on the unified model.** Pre-v0.4.36
   data is contaminated by the model asymmetry. The clean comparison
   starts from the first cron after this commit deploys.
2. Update `.env` on the VPS — copy `MASF_MODEL_MAIN` and `HERMES_MODEL`
   from the new `.env.example`.
3. `docker compose build masfactory hermes && docker compose up -d` to
   pick up the change.

### What to write in the thesis

- §3.4 — *"Both systems run on `qwen/qwen3-next-80b-a3b-instruct:free`
  via OpenRouter. The default was settled in v0.4.36 after a six-step
  failure chain (v0.4.30→v0.4.35) documented in
  `docs/iterations/`. Reasoning models (Nemotron Super 120B,
  gpt-oss-120b) were ruled out by an upstream Hermes parser limitation;
  popular free-tier instruct models (Llama 3.3 70B) by rate-limit
  collapse; smaller models (Llama 3.2 3B) by insufficient
  classification capability. Qwen3 Next 80B is the smallest viable
  instruct model with tool-calling support on a free provider as of
  2026-06-23."*
- §4.1.4 — *"Pre-v0.4.36 System B runs used Llama 3.2 3B, a model 40×
  smaller than System A's Nemotron 120B. Cross-system signal counts
  from before 2026-06-24 mix architecture effects with model-class
  effects and are not comparable. The §3.5 numbers above use the
  post-v0.4.36 window only."*

## Threats to validity touched

- Removes the comparison-validity defect from R-1 (Phase 10
  re-verification).
- Introduces a new dependency on Qwen3 Next remaining on the
  OpenRouter free tier; if it moves to paid, the script default
  switches automatically via the `HERMES_MODEL` env override.
- The model swap creates a "before" and "after" boundary inside the
  evaluation window. Per `docs/pre-registration.md` §7 (acceptable
  deviations), this counts as an "operational" deviation and is logged
  in `docs/session_log.md` and acknowledged in §4.1.4.
