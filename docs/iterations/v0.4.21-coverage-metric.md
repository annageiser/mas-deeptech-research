# v0.4.21 — Coverage metric (B.3)

**Date**: 2026-06-12
**Closes**: task #101 (B.3 — Coverage metric: signals/actor/week per source_kind)

## Why this exists

Without a coverage view, the per-system "signals collected" counter on
`/compare` looks impressive but hides the question that actually matters:

> Are we collecting *evenly* across the 40 seeded actors and across all
> four source types (arXiv / website / news / patent)?

A corpus dominated by 3 prolific universities × 1 source kind (website)
weakens every downstream Ehrenthal-derived metric — cheap-talk ratio,
credibility, momentum all become "what the 3 best-scraped actors said,"
not "what the Swiss-quantum ecosystem is signalling."

## What ships

### New endpoint `GET /api/coverage?system=&days=`

Returns:
- `summary` — total signals, actors with ≥1 signal, coverage %, distinct
  weeks, distinct source kinds (of the 5 the schema allows).
- `per_source_kind` — ecosystem-wide donut data (arxiv / website / news /
  swissreg / manual + their counts and pct).
- `per_actor` — one row per **seeded** actor (including those with zero
  signals — those are the gaps the metric exists to surface). Each row
  carries `total`, `weeks_active`, `source_kinds`, and the per-source-kind
  grid.
- `weekly` — ISO-week throughput (`2026-W23` style), each with a
  per-source-kind breakdown.

Implementation: `systems/api/api_app/coverage.py` (read-only aggregation
over `da.signals()` + `da.actors()`). No schema changes — both columns
(`actor_slug`, `source_kind`, `inserted_at`) already exist.

### New page `/coverage`

`systems/web/src/app/coverage/page.tsx` renders:
- 4 top stats (Total / Coverage % / Weeks / Source kinds).
- Donut of the source-kind mix.
- A simple per-week throughput table (last 13 ISO weeks).
- A per-actor table with an inline stacked bar showing each actor's
  source distribution.
- A "Gap" card listing seeded actors that produced **zero** signals in
  the window — these are the manual-spot-check targets.

Nav entry: under "Drill down" → "📡 Coverage".

## What this is NOT

- **Not** a runtime side-effect — purely a new read endpoint + page.
- **Not** a substitute for `/signals` filtering: this view aggregates,
  the signals page shows individual rows.
- **Not** wired to the cron/collector pipelines — it reflects whatever
  ends up in `public.signals` and surfaces blind spots after the fact.

## Threat-to-validity it touches

Closes one row in `docs/threats-to-validity.md` (implicit): "we report
total signal counts without showing per-actor distribution." After
v0.4.21 the gap card and per-actor distribution make this distribution
visible at a glance. The doc should mark this resolved on next pass.
