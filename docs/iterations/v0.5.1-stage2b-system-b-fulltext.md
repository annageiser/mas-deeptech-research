## 1. What this changes and why

The v0.5.0 arc unified the two systems' **search** substrate on self-hosted
SearXNG. One comparability gap remained: **evidence depth**.

- **System A (MASFactory)** scrapes full page text — `httpx` + `selectolax`,
  `collection/website.py::_visible_text`.
- **System B (Hermes)** saw **search snippets only**. SearXNG is search-only
  (`supports_extract() == False`), and so is `ddgs`; the agent's built-in
  `web_extract` tool had **no extract backend**, so it errored with
  "search-only backend cannot extract".

Snippet-only evidence hurts R2 (grounding), R5 (exact URL + verbatim quote),
and downstream `signal_type` / `dimension` / `published_at` assignment — and it
confounds the A-vs-B comparison (different evidence depth, not just different
orchestration).

**This change gives System B full-text extraction using the *same method* as
System A**, so the measured A-vs-B difference isolates the paradigm
(modular graph vs agentic loop), not the evidence layer.

## 2. Mechanism — a `web_extract` provider, not a skill

The v0.5.0 design proposed a `scrapling` **skill**. That was abandoned
(see the 2026-07-09 handoff): scrapling is heavy (Playwright/curl_cffi/camoufox)
and its extractor returned near-empty on real actor pages; and it left an
unresolved blocker — whether the agentic loop (toolsets `web,skills`, no
terminal) can execute a skill CLI at all.

We use a cleaner mechanism: a **web-extract provider plugin**. Hermes already
exposes a first-class `web_extract` tool (the model is even nudged to prefer it);
it dispatches to whichever provider `web.extract_backend` names, calling
`provider.extract(urls, format=...)`. We register a provider whose `extract()`
does a plain `httpx` GET + `selectolax` parse — **System A's method** — and
point `web.extract_backend` at it. No skill-CLI execution, no new tool in the
surface, no Playwright. The unresolved "can the agent run a skill CLI" question
is **sidestepped entirely**.

### 2.1 The backend-router shim (load-bearing)

Upstream's per-capability router (`tools/web_tools.py::_get_capability_backend`)
only honours a configured `web.extract_backend` when `_is_backend_available(name)`
returns True — and that function **hardcodes** the built-in backend names
(exa/parallel/firecrawl/tavily/searxng/brave-free/ddgs/xai), returning False for
anything else. A plain `web.extract_backend: localextract` would therefore be
**silently dropped**, and the router would fall back to search-only SearXNG.

So the **Dockerfile appends** a 6-line wrapper to `tools/web_tools.py` that
redefines `_is_backend_available` to recognise `localextract` (delegating to the
original for every other name). Key point on **timing**: `web_extract_tool`
resolves the backend (`_get_extract_backend`) **before** it triggers plugin
discovery (`_ensure_web_plugins_loaded`). Discovery is lazy — the `web` toolset
is static, so agent startup doesn't trigger it; the first web tool call does. A
runtime monkeypatch installed from the plugin (i.e. at discovery time) would
therefore **miss** a `web_extract` issued before the first `web_search` (the
prompt hands the agent the actor's `Website` URL, so an extract-before-search is
possible) — the first such call would error with "search-only backend cannot
extract". Appending to the module instead applies the change at **import time**,
before any discovery, so the very first extract resolves correctly regardless of
tool order. The append is idempotent (guarded by a marker), asserted in a fresh
interpreter at build time (fails the build loudly if the upstream symbol ever
moves), and is the only edit to an upstream file — the base image digest is
still cited; our two Dockerfile layers (this shim + the provider) are the delta.

*(History: this shipped first as a runtime monkeypatch in the plugin's
`__init__.py`; code review flagged the discovery-timing hole above, so it moved
to the build-time append.)*

## 3. Comparability (the thesis point)

`plugins/web/localextract/_html.py::visible_text` is a byte-for-byte
re-implementation of System A's `_visible_text`: same tag-strip set
(`script, style, noscript, header, footer, nav`), same
`HTMLParser(html).text(separator=" ", strip=True)`, same 12 000-char cap, same
User-Agent. It is a **separate implementation** — the comparison-validity
invariant forbids System B importing `masfactory_system` code — but the
**method is identical**, which is exactly what makes the two systems' evidence
layers comparable. Both systems now: search the same SearXNG, fetch full text
the same way, and differ only in orchestration.

## 4. Verbatim-fidelity note (honest limitation)

`web_extract_tool` runs an optional LLM-summarisation pass (auxiliary model =
our free `llama-3.3-70b:free`) over any extracted page longer than ~5 000 chars,
replacing `content` with a summary while keeping `raw_content` verbatim; shorter
pages stay verbatim. The agent ultimately receives `{title, content, error}`, so
for long pages the `evidence_quote` it copies may be a near-paraphrase rather
than an exact substring. This is **acceptable and comparable**: System A's
Extractor also reads page text through an LLM before emitting signals. The
SKILL.md instructs the agent to prefer a verbatim passage from the extracted
text; where the page was summarised, the quote is best-effort. Documented here
so §3.5 quality metrics (exact-URL %, verbatim-quote fidelity) interpret B's
numbers correctly.

## 7. Risks / trade-offs

- **Base-image drift.** The plugin is copied into the pinned image's bundled
  plugins dir; if a future base bump moves that dir, the build-time assertion
  fails loudly (by design) rather than silently reverting to snippets.
- **Upstream-internal coupling.** The shim depends on the name
  `tools.web_tools._is_backend_available`. The Dockerfile append asserts the
  symbol exists (`assert "_is_backend_available" in src`) and re-checks the
  behaviour in a fresh interpreter, so a base-image change that moved/renamed it
  **fails the build loudly** rather than silently reverting to snippets. Pinned
  digest → stable in practice.
- **Latency.** Full-text fetch adds a few HTTP GETs per actor (bounded: the
  agent extracts only its 2–4 best hits, `max_turns: 20`, 1 req/s/host). Far
  lighter than the abandoned Playwright path.
- **Politeness/ToS.** robots.txt respected (explicit Disallow blocks), honest
  UA, 1 req/s/host, public pages only (upstream SSRF filter runs first). robots
  is fetched via **httpx with a bounded 10 s timeout** — *not* the stdlib
  `RobotFileParser.read()`, whose `urllib` fetch has no timeout and could hang
  the whole extract() batch on a host that blackholes `/robots.txt`. We fail
  *open* on robots fetch error/timeout/non-200 (vs System A's fail-closed) so a
  transient hiccup doesn't blank evidence for a URL the agent already surfaced.

## 8. Eval impact

Extraction changes System B's evidence depth, so it belongs to the **same
`v0.5.0` clean-comparison window** the retrieval-alignment arc opened (treat
pre-v0.5.0 as baseline). Expected post-change shifts for B, per the §7 metrics
of the design doc: higher % of exact article `source_url`s, better
`published_at` coverage, and higher mean `confidence` on read-in-full signals.
