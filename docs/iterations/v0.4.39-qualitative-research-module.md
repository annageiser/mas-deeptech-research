## What ships

A round-trip between `public.signals` and any REFI-QDA-compliant
qualitative-analysis tool — built around the **REFI-QDA 1.5 exchange
standard** rather than any single tool's native format. The recommended
primary tool is **QualCoder**; **OpenQDA**, ATLAS.ti, NVivo, MAXQDA
are usable without any additional code on our side.

Four CLI sub-commands under `python -m eval_app.qda`:

```
export    sample stratified signals → produce a .qdpx
import    read a coded .qdpx → write data/gold/labels.yaml
compare   pairwise Cohen's κ between two labels.yaml files
status    stratified-cell counts for one labels.yaml
```

The .qdpx file is a ZIP container holding a REFI-QDA `project.qde` XML
plus one plain-text source per sampled signal. Any of the five tools
above will open it; coders apply codes; the same tool exports a new
.qdpx; we import it back into the gold-set YAML the evaluation harness
already consumes.

## Architecture decision — why REFI-QDA, not QualCoder's native format

The brief asked to evaluate QualCoder vs OpenQDA. The right question
turned out to be different: **the real abstraction layer is the
exchange standard, not the tool.**

REFI-QDA (Rotterdam Exchange Format Initiative for Qualitative Data
Analysis) is an XML-in-ZIP container standardised across:

| Tool | REFI-QDA support | Stack | Maturity |
|---|---|---|---|
| QualCoder | yes (read + write) | Python / SQLite / PyQt | 7+ y, peer-reviewed citations |
| OpenQDA | yes (improving) | Laravel + Vue + MariaDB | 1–2 y |
| ATLAS.ti | yes | proprietary | industry standard |
| NVivo | yes | proprietary | industry standard |
| MAXQDA | yes | proprietary | industry standard |

Building one importer/exporter per tool would duplicate effort and
gain nothing: the tools already agree on REFI-QDA as the interchange
format. So we implement REFI-QDA once and inherit all five tools.

### Why QualCoder is the recommended primary tool

1. **Stack alignment.** QualCoder is Python with a SQLite back-end —
   the same stack as the rest of this repo. OpenQDA is PHP / Laravel
   / Vue / MariaDB and would be a foreign body. We never need to read
   QualCoder's source, but understanding its REFI-QDA behaviour (in
   `qualcoder/qualcoder/refi.py`) only requires reading Python.
2. **Local-first single user.** This is a solo thesis. QualCoder runs
   on Anna's MacBook with no server, no auth, no network. OpenQDA
   needs a hosted instance.
3. **Maturity.** QualCoder is 7+ years old and cited in published
   qualitative-research methodology papers. OpenQDA is newer (most
   commits 2024–2026).
4. **Defensibility.** GPL-3 license, open repository, REFI-QDA
   conformance audited in the upstream repo's CI. Easier to cite in a
   thesis appendix than a younger project.
5. **Reproducibility.** A QualCoder project is a single SQLite file
   plus a sources folder — checkpointable into git LFS, copyable for
   intra-rater protocol (see below).

OpenQDA is **not excluded**. The `.qdpx` we produce opens in OpenQDA
unchanged. If a future iteration wants OpenQDA (e.g. for a
multi-coder workflow with cloud sync), no code changes are needed;
the operator just opens the same file in OpenQDA instead.

### Why the existing /labels page is NOT a qualitative-research tool

`/labels` (v0.4.37) is an editorial CRUD over `public.manual_signals`
— Anna's curated examples that feed *into* both producer systems as
training signal. It is not a coding tool: no categories, no memos,
no coded segments, no inter-rater workflow.

The QDA module operates on `public.signals` (output of the producers)
and produces `data/gold/labels.yaml` (input to the eval harness). It
is the opposite direction of the data flow. The two layers do not
interact and can ship independently.

## The codebook the coder sees

`schema.yaml` is the single source of truth for the four-signal
taxonomy. The codebook generator (`build_codebook`) reads it and
renders four top-level **categories** (signal_types) with their **19
dimensions** nested underneath:

```
Legitimacy
  leadership_expertise, patents, publications, awards, testimonials,
  educational_outreach, funding_event, regulatory_recognition
Customer co-creation
  collaborations_applications, pilots_pocs, customer_training
Community ecosystem
  cloud_platform_listings, hpc_collaborations, industry_partnerships,
  academic_partnerships
Future trajectory
  roadmaps, milestones, technological_advances, long_horizon_claims

Defense flags (siblings — v0.4.19 boolean overlay)
  Defense engagement
  Defense ambivalence

Quality flags (gold-set protocol)
  Keep — worth keeping
  Drop — should have been filtered
  Actor attribution correct
  Actor attribution wrong
```

GUIDs are stable UUIDv5 from a project namespace + code name so the
same code always gets the same GUID across exports — required for
REFI-QDA to merge codings reproducibly when Anna re-codes a subset.

## The coder's rule (encoded in the importer)

For each signal source the coder applies:

- **EXACTLY ONE** signal_type code (4 categories)
- **EXACTLY ONE** dimension code, and it MUST be a child of the
  chosen signal_type
- **0..N** defense flags (set only when evidence is explicit)
- **EXACTLY ONE** keep/drop code
- **EXACTLY ONE** actor-attribution code

The importer validates every rule and skips rows that fail, printing
the reason. Partial coding produces a partial `labels.yaml` — useful
when Anna runs `python -m eval_app.qda compare` mid-coding to see how
her in-progress decisions agree with the systems.

## End-to-end workflow

```
                       ┌────────────────────────┐
                       │ Supabase public.signals │  (System A + System B output)
                       └──────────┬─────────────┘
                                  │
                                  ▼
            python -m eval_app.qda export --out gold.qdpx --window-days 28
                                  │
                                  ▼
                         gold.qdpx + gold.seed.txt  (deterministic — pre-reg §5)
                                  │
                                  ▼
                       open in QualCoder (or any REFI-QDA tool)
                                  │
                       Anna applies codes per the rule above
                                  │
                                  ▼
                         coded.qdpx  (QualCoder export)
                                  │
                                  ▼
            python -m eval_app.qda import coded.qdpx --out data/gold/labels.yaml
                                  │
                                  ▼
                       data/gold/labels.yaml
                                  │
                                  ▼
                    python -m eval_app.runner cls
                                  │
                                  ▼
                  results.md + results.json    (Cohen's κ vs A, vs B)
```

Then for **intra-rater κ** (pre-reg §5, 7-day cooling-off):

1. After round-1 coding, save the .qdpx as `labels_round1.qdpx`,
   import to `labels_round1.yaml`.
2. Wait 7 days.
3. Re-code the same export (open the original `gold.qdpx` fresh in
   QualCoder, ignoring round-1's decisions).
4. Save as `labels_round2.yaml`.
5. `python -m eval_app.qda compare labels_round1.yaml labels_round2.yaml`
   → intra-rater Cohen's κ per axis.

For **inter-rater κ** (Backlog P1 #11, supervisor):

1. Send `gold.qdpx` to the supervisor.
2. They code (e.g. only 10 of the 50 signals).
3. Their export comes back as `gold_supervisor.qdpx`.
4. `python -m eval_app.qda import gold_supervisor.qdpx --out labels_supervisor.yaml --coder anna`
   reads Anna's codings; `--coder supervisor` reads the supervisor's.
5. `python -m eval_app.qda compare labels.yaml labels_supervisor.yaml`
   → inter-rater Cohen's κ on the 10-signal overlap.

The same .qdpx file can carry multiple coders' decisions
simultaneously (REFI-QDA's `creatingUser` attribute on each
`<Coding>` element). Our importer filters by coder so each YAML
output is single-rater clean.

## Comparison methodology (the thesis chapter section)

Three streams of categorical labels are produced per gold signal:

```
                gold_signal_type   gold_dimension   gold_keep   gold_actor_correct
  Anna  (gold)        L                 patents       True            True
  System A          C                 patents         True            True
  System B          L                 publications     True            True
```

The classification-quality metric (already in
`eval_app/metrics/classification_quality.py`) computes per-axis
precision / recall / macro-F1 / accuracy / Cohen's κ for each system
vs the gold stream. v0.4.39 adds:

- **κ(round1, round2)** — intra-rater reliability (this module).
- **κ(Anna, supervisor)** — inter-rater reliability (this module).

Threshold interpretation (Landis & Koch 1977, the standard in
quantitative content analysis):

| κ range | Strength of agreement |
|---|---|
| < 0.00 | Poor |
| 0.00–0.20 | Slight |
| 0.21–0.40 | Fair |
| 0.41–0.60 | Moderate |
| 0.61–0.80 | Substantial |
| 0.81–1.00 | Almost perfect |

Pre-reg §1 (H3) sets the absolute F1 gap on the macro-F1 axis at
0.15 between systems; this module supplies the κ leg of the same
H3 evaluation but the threshold is the standard Landis & Koch reading
(not a pre-reg falsification number).

## Limitations

1. **Plain-text sources only.** The exporter renders each signal as a
   single .txt file. Full-page HTML or PDF screenshots are not packed
   into the .qdpx — the coder works from title + URL + evidence_quote
   + summary, NOT the full original page. For five-deep-context signals
   (long ETH press releases, multi-page SNF call documents), the coder
   should open the source URL in a browser. Acceptable trade-off for
   the corpus size we're handling; would not scale to 1000+ signals.

2. **Whole-document selections only.** Each signal IS one "source"
   from REFI-QDA's perspective, so the codings apply to the whole
   document — there is no sub-document segmentation. This matches
   how `public.signals` is structured (one signal = one event), but
   means we cannot use QualCoder's text-highlighting workflow to
   pinpoint *which sentence* triggered each code. For the thesis's
   gold-set use-case this is the right granularity; for future
   qualitative-deepening work (e.g. discourse analysis of vendor
   communications) the segmentation layer would need to be added.

3. **No images, no rich-media coding.** The Defense ambivalence
   case sometimes leans on what an actor visually omits in marketing
   material. Our .qdpx pack only carries text. A future iteration
   could add `<PictureSource>` / `<AudioSource>` per the REFI-QDA
   spec — out of scope for v0.4.39.

4. **GUID stability assumes the namespace stays constant.** Re-running
   the exporter with the same signal IDs produces the same GUIDs,
   so a coded .qdpx remains importable across re-exports. Bumping
   the namespace UUID (in `codebook.py` and `refi_qda.py`) would
   invalidate all previously-coded .qdpx files. We treat the
   namespace UUID as a stable contract (documented at the top of
   both files).

5. **Multi-coder conflict resolution is not automatic.** When a
   single .qdpx carries both Anna's and the supervisor's codings,
   the importer extracts each coder's view separately. There is no
   built-in "resolve disagreement" step — the κ value IS the
   summary of disagreement; resolution happens in a human meeting,
   then Anna re-codes the affected rows.

6. **Sample-size constraint.** The stratified sampler targets 50
   signals across 16 cells (4 actor categories × 4 signal types).
   When a cell holds fewer than the per-cell quota in the live
   corpus, the sampler takes what's there and refills from a
   leftover pool. The exporter prints per-cell counts so the
   pre-reg §5 ≥3-per-cell requirement is visible at sample time. If
   a cell has zero signals, that's a corpus distribution finding
   worth flagging in §3.5.

7. **OpenQDA round-trip not yet end-to-end tested by us.** OpenQDA
   advertises REFI-QDA import/export but its v1.x conformance is
   newer than QualCoder's. We have NOT manually verified that an
   Anna→OpenQDA→Anna round-trip preserves every code. The .qdpx we
   emit follows the 1.5 spec, but any tool-specific quirks would
   surface only in actual use. Recommended path for OpenQDA today:
   open the .qdpx, verify the codebook is intact, code one signal,
   re-export, and run `python -m eval_app.qda import` to confirm
   the round-trip survives.

## Deployment

No container rebuild required for the producer / API / web side. The
eval module runs inside the `reports` container which already has
the deps. To use:

```bash
# 1. Sample + write .qdpx
docker compose run --rm \
    -v /tmp/qda:/tmp/qda \
    reports python -m eval_app.qda export \
        --out /tmp/qda/gold-$(date -u +%F).qdpx \
        --window-days 28 \
        --sample-size 50 \
        --seed 42

# 2. Anna pulls the .qdpx to her laptop, codes it in QualCoder.
scp <vps>:/tmp/qda/gold-…qdpx ./gold.qdpx
# … code in QualCoder, export as gold-coded.qdpx …

# 3. Push back + import
scp ./gold-coded.qdpx <vps>:/tmp/qda/
docker compose run --rm \
    -v /tmp/qda:/tmp/qda \
    -v $(pwd)/systems/evaluation/data:/data/eval-gold \
    reports python -m eval_app.qda import \
        /tmp/qda/gold-coded.qdpx \
        --out /data/eval-gold/gold/labels.yaml \
        --show-summary

# 4. Run the existing eval harness — classification_quality picks
#    labels.yaml up automatically.
docker compose run --rm reports python -m eval_app.runner cls --window-days 28
```

Anna's laptop side: install QualCoder

```bash
# QualCoder >= 3.5 has REFI-QDA 1.5 import/export.
pipx install qualcoder
qualcoder &   # opens GUI; File → Import REFI-QDA project
```
