# v0.4.20 — System B embeddings + the prereq path to M.1 (semantic dedup)

**Date**: 2026-06-12
**Trigger**: Recommendation #1 from `docs/system-tech-comparison.md`. System A has had `fastembed` + BGE-base-en-v1.5 (768d) embeddings since v0.4.1 (#52); System B had none. Without embeddings on B, semantic dedup can only work for A, biasing the per-system comparison toward "B has more signals than A" — but only because A is deduping and B can't.

## What changed

Hermes wrapper image now installs `fastembed>=0.4.0` in the upstream venv (~210 MB image growth). Persister gets two new functions vendored from MASFactory:

- `_embed_text(text)` — lazy-loads fastembed on first call; returns `None` when `HRM_EMBEDDINGS` is unset; gracefully returns `None` if fastembed isn't installed.
- `_compose_signal_text(signal)` — **identical** composition to `systems/masfactory/.../embedding.py:compose_signal_text`: `title` + `evidence_quote` + `summary` + `dimension:<key>` joined by `\n`. Same composition means System A and System B signals about the same event embed to nearby points.

Each row inserted by `persist_signals.py` now includes an `embedding` field when `HRM_EMBEDDINGS=1` is set in `.env`.

### Why "vendored", not imported

Comparison-validity invariant says System B's persister must not import from `masfactory_system`. The composition function is ~10 lines; vendoring is the right call even though it duplicates a tiny bit of code. Both copies must stay in sync; comments in both files cross-reference.

## What didn't change

- The model: still `BAAI/bge-base-en-v1.5` (768d). Same in both systems.
- The composition string: identical. Same in both systems.
- The schema: `signals.embedding vector(768)` already exists since v0.4.1. No migration needed.
- System A's behaviour: untouched. `MASF_EMBEDDINGS=1` still works the same way.

## Files changed

- `systems/hermes/Dockerfile` — adds the `uv pip install fastembed>=0.4.0` line after the ddgs install.
- `systems/hermes/scripts/persist_signals.py` — `_embed_text` + `_compose_signal_text` helpers; row builder calls them when `HRM_EMBEDDINGS=1`.
- `docker-compose.yml` — hermes service environment block forwards `HRM_EMBEDDINGS` from host env to container.

## Unit tests

```
✓ compose_signal_text matches MASFactory
✓ embeddings off by default (HRM_EMBEDDINGS unset)
✓ HRM_EMBEDDINGS=1 but no fastembed → returns None gracefully
```

(Fastembed not installed in the dev Mac; the production Hermes image will have it.)

## The path to M.1 (task #113)

This commit is the **prerequisite** for M.1 — "Turn on semantic dedup in production + backfill historical duplicates". With embeddings now computable on both systems, M.1 becomes a 3-step operational task:

### Step 1 — Backfill embeddings on existing signals

```sql
-- Verify how many signals lack an embedding
SELECT system, count(*)
FROM public.signals
WHERE embedding IS NULL
GROUP BY system;
```

Then run the per-system backfill scripts:

```bash
# System A — backfill existing MASFactory rows
docker compose run --rm \
  -e MASF_EMBEDDINGS=1 \
  --entrypoint python masfactory \
  -m masfactory_system.cli backfill-embeddings

# System B — same idea, but requires a new helper since the Hermes
# wrapper doesn't currently have a backfill subcommand. Quickest path:
# write data/raw/hermes_backfill_embeddings.py that selects rows where
# system='hermes' AND embedding IS NULL, computes them in batches of 50,
# and PATCH-updates via Supabase REST.
```

(A future v0.4.21 commit could add the backfill helper to `systems/hermes/scripts/` so both systems share the same "fill the gaps" UX.)

### Step 2 — Turn semantic dedup ON in `.env`

```env
MASF_EMBEDDINGS=1
MASF_SEMANTIC_DEDUP=1
MASF_SEMANTIC_DEDUP_THRESHOLD=0.92
MASF_SEMANTIC_DEDUP_DAYS=90

HRM_EMBEDDINGS=1
HRM_SEMANTIC_DEDUP=1
HRM_SEMANTIC_DEDUP_THRESHOLD=0.92
HRM_SEMANTIC_DEDUP_DAYS=90
```

### Step 3 — Restart + watch

```bash
docker compose build hermes masfactory   # picks up fastembed
docker compose up -d
```

Then on the next cron tick (or a `docker compose run --rm hermes` manual smoke), dropped-via-semantic-dedup signals get logged to `data/raw/runs/<ts>/semantic_dedup.json` (System A) and `state/runs/<UTC-iso>/persist.log` (System B).

### Acceptance for M.1

Cross-system signal count is no longer confounded by "B doesn't dedup". The `/compare` page's `signals` metric reflects actual signal count, not dedup-status difference.

## Threats to validity touched

Closes one item documented in `docs/threats-to-validity.md` (implicit): "B's signal count appears higher than A's because A is deduping more aggressively." After M.1 with both `*_EMBEDDINGS=1` + both `*_SEMANTIC_DEDUP=1`, this confound is gone. Update the doc to mark it resolved once the backfill is applied.
