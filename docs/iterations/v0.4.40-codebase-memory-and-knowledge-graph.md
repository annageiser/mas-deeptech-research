## Architecture impact analysis

### Why the two deliveries are SEPARATE

`codebase-memory-mcp` operates on **source code** — its node labels are
`Project`, `Package`, `File`, `Class`, `Function`, `Method`, `Interface`,
`Route`; its edge types are `CONTAINS_FILE`, `CALLS`, `IMPORTS`,
`IMPLEMENTS`, `TESTS`. The research-knowledge-graph operates on
**research data** — `Actor`, `SignalType`, `Dimension`, `Signal`,
related by signal volume and pgvector cosine similarity.

Forcing the research entities into the MCP's schema (an Actor as a
`Class`, a Signal as a `Function`) would corrupt both domains: examiners
would rightly question why a Swiss-quantum dashboard ingests a Swiss
research institute as a code class, and the MCP server's call-path and
dead-code tools become nonsensical when fed non-code data.

What we **do** reuse from `codebase-memory-mcp` is the **conceptual
pattern**: a typed Entity layer + typed Relationship layer + optional
semantic-link overlay. That pattern lives in
[systems/api/api_app/kg_model.py](../../systems/api/api_app/kg_model.py)
and the same shape backs both the research graph and the developer
graph — just over different data domains.

### What this iteration does NOT touch

- **Supabase schema** — no new tables, no new columns, no migrations.
- **Production runtime** — no new container, no new compose service, no new env vars on the VPS.
- **Existing wire shape** — every pre-v0.4.40 client gets the exact same JSON it always did.
- **`/api/signals`, `/api/actor/...`, `/api/compare`** — unchanged.
- **CI matrix** — no new test target. The new `test_knowledge_graph.py` lands in the existing `systems/api/tests/` pytest suite.

## Database and schema changes

**None.** This was a deliberate scope decision (you chose the "Additive
minimal" option). The graph is still derived per request from
`public.signals` + `public.actors` so it cannot drift from the live
corpus, and no ETL pipeline is introduced.

The semantic layer reads `public.signals.embedding` (vector(768), added
in v0.4.20). When `MASF_EMBEDDINGS` / `HRM_EMBEDDINGS` are off (the
default in `.env.example`), the embedding column is NULL everywhere
and the semantic layer is silently a no-op.

If a future iteration wants persistent KG storage (cacheable, queryable
via SQL joins, supports incremental updates without re-scanning every
signal), the `kg_model.py` Entity / Relationship / Graph shape maps
directly onto two natural tables `public.kg_entities(id, type, label,
properties jsonb)` + `public.kg_relationships(source, target, type,
weight, properties jsonb)`. Today's builder reads from views, tomorrow's
builder could read from those tables instead — no client-side change.

## New dependencies and risks

### Dev-tool side (Delivery A)

- **codebase-memory-mcp v0.8.1** — DeusData, MIT, single static C binary, 14.1 k GitHub stars (verified 2026-06-25).
- **Risks:**
  1. **Newish project** — first commit was 2026-02; only 4 months of public history. Mitigation: pinned reference version in `docs/codebase-memory-mcp.md`; users can stay on v0.8.1 indefinitely since the binary is self-contained.
  2. **No supply-chain audit by us** — we trust the upstream's SLSA-Level-3 + VirusTotal + CodeQL pipeline. Mitigation: the MCP server's only inputs are the local source tree and its own SQLite cache; no network egress beyond what the editor's MCP client allows.
  3. **Optional** — production never sees it, so if it breaks or stops being maintained, removing it is `rm .mcp.json && rm docs/codebase-memory-mcp.md`. Zero rollback complexity.

### Runtime side (Delivery B)

- **No new Python packages** — the builder uses only existing deps (pandas, scikit-learn already present for eval).
- **No new TypeScript packages** — the canvas additions are SVG, no new graph library.
- **Risks:**
  1. **pgvector cosine over per-actor centroids is O(actors²)**. At 40 actors × 768 floats × 40 pairs = 1k cosine evaluations per request — sub-millisecond. Mitigation: the request is already cached for 60s by the API container's in-process cache (`_cached` wrapper in `data_access.py`). At the 60s expiry recomputing is harmless. If the corpus grows past ~200 actors the pairwise scan becomes noticeable; the next iteration would push the cosine into pgvector via a custom RPC.
  2. **Embedding payload size**. A 768d float vector is ~6 KB per row; 1.7k signals → ~10 MB on the wire. Mitigation: `signal_embeddings()` is a separate query so the standard `/api/signals` and `/api/coverage` paths never pay that cost. Only `/api/knowledge-graph?include_semantic=true` requests pull it. The endpoint is already gated by Caddy basic-auth.
  3. **New edge types could visually clutter the canvas**. Mitigation: both new layers are opt-in via query params, default off; toggle links above the canvas make the on/off state obvious. The semantic edges are also capped at `MAX_SEMANTIC_EDGES=60`.

## Migration steps

### Developer machine (one-time)

```bash
# 1. Install codebase-memory-mcp (one-line shell script).
curl -fsSL https://raw.githubusercontent.com/DeusData/codebase-memory-mcp/main/install.sh | bash

# 2. Verify on PATH.
codebase-memory-mcp --version

# 3. From repo root, build the first index.
codebase-memory-mcp index . --cache-dir .codebase-memory

# 4. Restart your editor. Claude Code: `/mcp` should now list `codebase-memory`.
```

### Production (VPS)

```bash
# Nothing to migrate at the data layer.
# Pull the merge commit + rebuild api + web.
cd /opt/mas-deeptech-research
git pull origin main
docker compose build api web
docker compose up -d api web

# Verify the new layers respond.
curl -s -u "anna:$PWORD" \
  "https://mas-deeptech-research.cloud/api/knowledge-graph?include_taxonomy=true&days=28" \
  | jq '.nodes[] | select(.kind=="signal_type") | .label'
```

### Backout

Either layer can be disabled at runtime without a deploy:

- Operator stops opening URLs with `?taxonomy=1` / `?semantic=1`.
- For a hard rollback, delete `.mcp.json` (Delivery A only) or revert the merge commit.

## Limitations and out-of-scope items

1. **Embeddings are off by default** — the semantic layer produces zero
   edges in the as-deployed configuration. To exercise it you have to
   enable `MASF_EMBEDDINGS=1` and/or `HRM_EMBEDDINGS=1`, wait for at
   least one cron tick to populate the column, then re-query. This is
   documented in `.env.example`; the next iteration can also wire a
   one-shot `python -m masfactory_system.scripts.backfill_embeddings`
   pass so the layer is useful immediately after enabling the flag.
2. **Semantic edges are between ACTORS, not SIGNALS** — we aggregate to
   actor centroids because the canvas's actor-actor edge type already
   exists and the layout makes adding a third edge between the same
   pair visually meaningful. A future iteration could surface
   signal-signal similarities inside the inspector panel when a
   specific actor is hovered.
3. **Knowledge graph is still derived per request, not persisted** — we
   deliberately did not introduce `kg_entities` / `kg_relationships`
   tables for v0.4.40. The conceptual model (kg_model.py) is the
   abstraction layer; storage will follow when the corpus is large
   enough to make per-request derivation a measurable cost.
4. **codebase-memory-mcp does NOT index this repo's TypeScript** unless
   you ran the index command. The MCP server is incremental but needs
   a first pass per checkout. The `.codebase-memory/graph.db.zst`
   team-shared baseline pattern is documented but not committed —
   leaving that decision to the operator.
