# v0.4.9 — Always overwrite the seeded config + skill (THE actual fix)

**Date**: 2026-06-11
**Trigger**: Anna's seventh smoke after seven attempts hit the same OpenRouter 402. Per-actor stderr confirmed the model in flight was still `anthropic/claude-opus-4.6` with `max_tokens=128000` — i.e. NONE of the v0.4.5 / v0.4.6 / v0.4.7 / v0.4.8 config changes were actually being loaded by the running agent.
**Status**: shipped. Hard root-cause fix.

## What was actually happening

The upstream hermes-agent ships a `cli-config.yaml.example` (62 KB, default model `anthropic/claude-opus-4.6`). Upstream's `01-hermes-setup` cont-init hook copies this example to `$HERMES_HOME/config.yaml` **on every container start** if the file doesn't exist. Our `03-seed-swiss-quantum` hook runs *after* it, then skipped because the file already existed (`if [ ! -f "${CFG_DST}" ]`).

So no matter how many times we edited `systems/hermes/config/cli-config.yaml` and rebuilt the wrapper image, the volume ended up with upstream's 62 KB example, and the agent ran with **Claude Opus 4.6** as its default model on every call. That's why every 402 was identical (`max_tokens=128000`, can only afford 110819) — Claude Opus's native ceiling is 128k, and Anna's balance can only cover ~111k tokens at Opus's per-token rate.

Six full rounds of debugging (v0.4.5 through v0.4.8) edited a config that was getting silently clobbered on every restart. The verification SQL paths and per-actor stderr lookups never showed the model name explicitly, so the symptom kept presenting as "free-tier rate limit / credit hold issue" when in fact it was "the agent isn't reading our config at all."

## The two-part fix

### 1. seed-hermes-home.sh — always overwrite

```sh
# v0.4.4 — v0.4.8 (broken)
if [ ! -f "${CFG_DST}" ]; then
    cp "${SRC}/config.yaml" "${CFG_DST}"
fi

# v0.4.9 — always wins the race
cp "${SRC}/config.yaml" "${CFG_DST}"
```

Same change for the skill directory — always `rm -rf` + `cp -r`. The skill and config are part of the **artefact**, not user state. Custom edits to `$HERMES_HOME/config.yaml` in the volume by hand would be lost on the next container start. The supported customization path is editing `systems/hermes/config/cli-config.yaml` in the repo + image rebuild.

### 2. CLI overrides in `collect_all_actors.sh` — belt-and-braces

`hermes chat` CLI flags take precedence over config.yaml. Add explicit `--model` and `--provider` to every invocation so the cron loop forces the free Nemotron Nano slug regardless of what's in config.yaml:

```sh
MODEL="${HERMES_MODEL:-nvidia/nemotron-nano-9b-v2:free}"
hermes chat \
    --skills collect-swiss-quantum-signals \
    --toolsets web,skills \
    --model "${MODEL}" \
    --provider openrouter \
    -q "${PROMPT}"
```

If config.yaml ever falls back to upstream's example again (e.g., upstream changes the install order, or a future Dockerfile change drops our hook), the CLI flags still pin the model to free. There's no CLI flag for `max_tokens` though — that one's config-only — so we still need part #1 for the token cap.

## Honest retrospective

Six iteration docs (v0.4.5 – v0.4.8) for what turned out to be a single seed-hook bug. The mistake was not verifying the running config from inside the agent's actual process. Lessons for the thesis appendix:

1. **Don't trust "I edited the file" when a deployment automation might overwrite it.** Always grep the live config from the artefact, not the source.
2. **Add a config-version marker.** Future iteration: print the SHA256 of `$HERMES_HOME/config.yaml` from the cron-loop startup so any mismatch is obvious at a glance.
3. **CLI overrides are cheap belt-and-braces.** When two systems race to write a config file, having the CLI flags re-state the critical settings means the runtime can't drift silently.
