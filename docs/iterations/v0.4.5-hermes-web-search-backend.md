# v0.4.5 — Hermes web_search backend provisioning

**Date**: 2026-06-10
**Trigger**: First Phase-B smoke run on the VPS returned 0 signals across all 40 actors in ~30 s wall time. Agent output showed: *"The `web_search` and `web_extract` tools required by this skill are not available in this session."*
**Status**: Shipped. Anna needs to register for Tavily (or one of the alternates), drop the key in `.env`, then re-run the smoke.

## The bug

After the v0.4.4 rename (pattern → real CLI) landed, the cron loop ran end-to-end without errors but produced zero signals. The agent itself was healthy — it loaded our skill, made tool calls (`skills_list` succeeded in 0.0 s), and correctly followed the skill's quality rule #1 ("Never fabricate") by returning an empty `signals: []` JSON block whenever it couldn't gather evidence.

What it couldn't gather: anything from the web. `--verbose` mode on a one-off `hermes chat` inside the container exposed the root cause:

```
✅ Enabled toolset 'web': web_extract, web_search
DEBUG - Tool web_extract unavailable (check failed)
DEBUG - Tool web_search unavailable (check failed)
🛠️  No tools selected (all filtered out or unavailable)
Tools: 0
```

The toolset registers at startup, but each tool's per-call availability check fails. Reading `/opt/hermes/tools/web_tools.py` showed the check is a chain of `os.getenv` lookups across six search-provider backends, tried in priority order:

```python
("firecrawl",  _has_env("FIRECRAWL_API_KEY") or _has_env("FIRECRAWL_API_URL") or _is_tool_gateway_ready()),
("parallel",   _has_env("PARALLEL_API_KEY")),
("tavily",     _has_env("TAVILY_API_KEY")),
("exa",        _has_env("EXA_API_KEY")),
("brave-free", _has_env("BRAVE_SEARCH_API_KEY")),
# plus ddgs — needs the `ddgs` Python package, NOT in the upstream image
```

Our `.env` had none of those keys, so every backend failed, the tool stayed unregistered at call-time, and the agent ended up with `Tools: 0`. With no web tools, the skill's prompt ("use `web_search` and `web_extract`") was unsatisfiable, so the agent returned `signals: []` 40 times.

## Why this wasn't caught at v0.4.4 ship time

The Phase A local smoke only checked that the parser + shell wrapper + persister handled the JSON contract correctly. It used a mocked stdout. The actual agent invocation only happens inside the upstream image, which I never ran locally — that's the whole point of the two-stage build. So the missing env was a deployment-time finding, not a Phase-A finding.

The disposition's risk register did flag *"OpenRouter rate limits"* but didn't anticipate that the agent itself would require additional third-party SaaS APIs to function. Worth flagging in the threats-to-validity doc.

## Also fixed in this pass

While the env block was being touched, two latent issues:

1. **`HERMES_LIMIT_ACTORS` / `HERMES_LOOKBACK_DAYS` were never reaching the container.** Docker Compose only forwards shell env vars that appear in the service's `environment:` block. The Phase-A smoke command `HERMES_LIMIT_ACTORS=3 ... docker compose run --rm hermes` was silently using container-side defaults (all 40 actors, 180-day window). Fix: add the two vars to the compose `environment:` block with `${VAR:-default}` interpolation.

2. **No `.env.example` documentation for the new web-search keys.** Added a dedicated section listing all six backend env vars + free-tier capacity numbers + recommended provider (Tavily). Mirrored in `docs/reproducibility.md` § *"Hermes web tools"*.

## Free-tier capacity math (drives the cron schedule)

40 actors × ~6 searches/actor per run:

| Cadence | Searches/month | Fits free tier? |
| --- | --- | --- |
| **Weekly** | 4 × 240 = 960 | ✓ Tavily / Exa / Brave / Firecrawl |
| Daily | 30 × 240 = 7,200 | ✗ exceeds every free tier |

The shipped `crontab.sample` is currently daily. With free-tier Tavily we should flip to weekly (`0 5 * * 1` = Mondays 05:00 Europe/Zurich) until/unless the supervisor wants to fund a paid tier. This is captured in the deployment runbook below.

```bash

# 5. Smoke (3 actors, 60-day window) — should now produce signals

# expect: per-actor "✓ <slug> — N new signals" with N > 0 on at least 1-2 actors

# 6. If green, flip the cron to WEEKLY before installing (free-tier capacity):
sed -i 's|^0 5 \* \* \*|0 5 * * 1|' systems/hermes/crontab.sample
sudo cp systems/hermes/crontab.sample /etc/cron.d/mas-deeptech-research-hermes
sudo chmod 0644 /etc/cron.d/mas-deeptech-research-hermes
sudo systemctl restart cron

# 7. Verify in Supabase
psql ... -c "SELECT count(*), max(collected_at)
             FROM signals
             WHERE system='hermes' AND collected_at > now() - interval '1 hour';"
```

## What goes in the thesis

Two paragraphs for Chapter 4.1.4 (Threats to validity → tooling assumptions):

> System B's web-search tooling depends on a third-party search-API provider (Tavily for the empirical-evaluation window). The free tier caps cron at weekly cadence; this is a reproducibility hazard for any future replicator who exceeds the free quota and an empirical-validity hazard insofar as Tavily's results may differ from the open-web URLs that MASFactory's `httpx`-based collectors reach. The runbook documents how to swap providers via a single env var (`EXA_API_KEY`, `BRAVE_SEARCH_API_KEY`, …) so the design choice is not load-bearing.

> A diagnostic discovered post-deployment: when the search-provider key is missing, upstream registers the `web` toolset but each tool's availability check silently fails, and the agent correctly refuses to fabricate signals (skill rule #1). The system therefore degrades to "produces zero signals" rather than "produces wrong signals" — a desirable failure mode for a research artefact, but one that took ~90 minutes of debugging to surface because the failure is silent at the cron-loop layer.
