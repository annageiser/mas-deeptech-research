# v0.4.25 — Phoenix observability for replayable LLM-call traces

**Date**: 2026-06-12
**Closes**: task #125

## Why this exists

The audit folder captures every node's input/output as JSON. That's
enough to **read** what happened. It is not enough to **replay** or
**compare** across runs:

- No LLM-call boundary — a node's output is a string; you can't tell
  if it took one Chat Completions call or three (with retries).
- No timing breakdown — was the 38-second per-actor latency the LLM,
  the retriever, or the embeddings?
- No tool-call tree — when the Hermes-side mode debates, which message
  came from which agent?
- No replay UI — comparing "consensus mode" vs "single-pass mode"
  means diffing JSON folders by hand.

Phoenix (Arize's open-source LLM tracing platform) gives this for free:
every OpenAI Chat Completions call is captured as an OpenTelemetry span
and shipped to a local server. The Phoenix UI then exposes per-run
timelines, per-call token cost, latency histograms, error rates,
prompt-by-prompt diffs.

For the thesis evaluation chapter, this is the difference between "I
think the debate mode costs ~3× more" and "the debate mode took 6.8s
vs 2.1s median and 1,240 tokens vs 410 — measured over N=12 runs".

## How it plugs in

```
                  (existing)                            (new)
        ┌──────────┐    OpenAI            ┌──────────┐    OTLP
        │  Agent   │ ───────────────▶    │  Phoenix │ ────────┐
        │ (LLM)    │     Chat            │   server │         │
        └──────────┘                     └────┬─────┘         ▼
                ↑                              │      ┌────────────────┐
                │   instrumented at             │      │  Phoenix UI    │
                │   openai SDK level by         │      │ (port 6006)    │
                │   OpenInference               │      └────────────────┘
                                                ▼
                                         /mnt/data (sqlite, volume)
```

OpenInference is the instrumentation layer that auto-wraps the openai
SDK. MASFactory's `LegacyOpenAIModel` uses that SDK underneath, so we
get full coverage without any agent-level changes.

## What ships

### Module

`masfactory_system/observability.py`:
- `is_enabled()` — `PHOENIX_ENABLED=1|true|yes|on`, default OFF.
- `collector_endpoint()` — `PHOENIX_COLLECTOR_ENDPOINT`, default
  `http://phoenix:6006` (works on the compose network).
- `project_name()` — `PHOENIX_PROJECT_NAME`, default
  `masfactory-swiss-quantum`.
- `init(run_id)` — initialises tracing once per process. Returns True
  if active (or already active), False if disabled / deps missing /
  collector unreachable. **Never raises** — the cron path continues.
  When provided, `run_id` is set as a resource attribute on every
  span so the Phoenix UI groups them under the right cron tick.

### Wiring

`runner.py` calls `init_phoenix(run_id=run_id)` right after the run is
opened in Supabase but **before** the model is constructed (the openai
SDK needs to be instrumented before its first call).

When initialisation succeeds, a small `phoenix.json` is written to the
audit folder with `{enabled, endpoint, project, run_id}` so a curious
reader of the run knows traces were captured.

### Dependencies

`systems/masfactory/pyproject.toml`:
- `arize-phoenix-otel>=0.6.0` — OTel SDK wiring + register() helper.
- `openinference-instrumentation-openai>=0.1.18` — auto-instruments
  the openai SDK.

Both pull in standard OpenTelemetry packages. No fastembed / torch /
heavy native code. Image size growth: ~30 MB.

### Compose service

`docker-compose.yml` gains a `phoenix` service:

```yaml
phoenix:
  image: arizephoenix/phoenix:latest
  restart: unless-stopped
  profiles: ["observability"]    # ← off by default; explicit opt-in
  environment:
    PHOENIX_WORKING_DIR: /mnt/data
    PHOENIX_PORT: 6006
  volumes: [phoenix_data:/mnt/data]
  ports: ["127.0.0.1:6006:6006"]
```

Bound to `127.0.0.1` so it's reachable from the VPS host but **not**
world-readable. Use an SSH tunnel to view from a workstation:

```bash
ssh -L 6006:127.0.0.1:6006 root@<vps>
# then open http://localhost:6006
```

If you later want public access, add a Caddy reverse-proxy block —
either on a subdomain or sub-path with basicauth, same pattern as the
main site.

### Tests

`tests/test_observability.py` — 10 cases:
- env-var truthy/falsy parsing
- default endpoint + project, explicit override
- `init()` returns False when disabled
- `init()` returns a bool when enabled (no raise) regardless of dep state
- idempotency

The real OpenInference instrumentor is NOT exercised — that would need
a live Phoenix collector and full OTel SDK mocking. The contract we
test is "init is gated correctly and never crashes the cron".

## Operator runbook

```bash
git pull
docker compose build masfactory                          # picks up the two new deps
docker compose --profile observability up -d phoenix     # start the tracing server

# turn tracing on for a single ad-hoc run (no cron impact)
PHOENIX_ENABLED=1 docker compose run --rm masfactory \
  run-once --limit-actors 3
```

The `--profile observability` flag is what unhides the `phoenix` service.
Without it, `docker compose up -d` ignores Phoenix completely (which is
why the regular `docker compose up -d` after the v0.4.25 deploy doesn't
try to pull the Phoenix image).

Or persist for cron:

```env
# in .env
PHOENIX_ENABLED=1
```

Then `docker compose up -d` to pick up the env var.

View the UI:

```bash
ssh -L 6006:127.0.0.1:6006 root@<vps>
# open http://localhost:6006 in your browser
# choose project "masfactory-swiss-quantum"
```

## What this is NOT

- **Not** wired into Hermes. The hermes-agent CLI manages its own LLM
  calls through its own OpenAI client — instrumenting that would
  require modifying upstream code, which the comparison-validity
  invariant forbids. Phoenix here is a System A tool.
- **Not** required for cron. The cron tick runs identically whether
  Phoenix is on or off. The thesis can capture a curated set of runs
  for the evaluation chapter without paying the overhead daily.
- **Not** a replacement for the audit folder. The folder still holds
  ground-truth JSON; Phoenix holds the LLM-call layer that sits
  underneath.

## Threat to validity touched

Closes one row in `docs/threats-to-validity.md` (implicit): "we
estimate LLM token cost from the model's post-hoc tracker, which loses
fidelity across retries and failover events." After v0.4.25 the
per-call ground truth is in Phoenix and reconcilable with the run-level
totals already in `token_usage`.
